## $(date +%Y-%m-%d) - Squared Distance Over Math.sqrt in Game Loops
**Learning:** Found a classic performance anti-pattern in high-frequency game loops (e.g. `potCheck` methods): using exact Euclidean distance `Math.sqrt(dx*dx + dy*dy) <= 9`. Since `Math.sqrt` is computationally expensive and precision for collision distance thresholds doesn't strictly need it, squared distance comparisons (`dx*dx + dy*dy <= 81`) achieve identical logical results without the CPU overhead. The codebase replicates this logic across multiple equivalent class variations (`client/Ball.java`, `jfx/Ball1.java`, `tcpobject/Ball.java`), making centralized fixes necessary. Additionally, JavaFX compiles must link modular dependencies carefully (`--module-path` and `--add-modules`), and older syntax or non-modular components (like `javax.jws.Oneway`) might cause local build issues on modern JDKs.
**Action:** When inspecting collision/hit detection methods in physics-heavy clients, prioritize replacing exact Euclidean distance thresholds (`Math.sqrt(...) <= r`) with squared distance comparisons (`(...) <= r*r`). Additionally, always verify functionality across all replicated packages (`client`, `jfx`, `tcpobject`, etc.) to prevent desyncing logic.
